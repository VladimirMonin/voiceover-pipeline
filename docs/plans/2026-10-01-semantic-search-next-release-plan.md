## 1. Зачем отдельный план 🎯

План разработки `2026-09-29` включает §8 «Поиск» и этап S09
(два embedding-backend, профили, кеш, `sqlite-vec`, hybrid). Планируемый, ещё не выпущенный
`v0.7.0` **сохраняет только полнотекстовый слой S08 (FTS5)**, а
семантику выводит за свой scope: `--mode semantic|hybrid` по-прежнему явно
отклоняется (`SEARCH_MODE_DEFERRED`, exit `2`).

Этот документ делает отложенную работу **самостоятельным исполняемым планом
следующего релиза**, а не «пустой заготовкой» и не скрытой частью `v0.7.0`.
Он опирается на уже зафиксированные офлайн-контракты S08 (роли текста,
`search_chunks`, `text_sources`, фильтры до `limit`, приватный `asr_context`)
и расширяет их производным векторным слоем.

Владелец **сознательно исключил** из `v0.7.0` embeddings, `sqlite-vec`,
semantic и hybrid. Любая реализация этих функций до закрытия этого плана и
его plan-gate запрещена.

### Что именно строится ✅

| Область | Обязательный результат следующего релиза |
|---|---|
| Локальный backend | Один локальный `Qwen/Qwen3-Embedding-0.6B` через необязательный `sentence-transformers` |
| Облачный backend | Один облачный `qwen/qwen3-embedding-8b` через Polza `/embeddings` |
| Query/document preprocessing | Явное различие query-инструкции и документа на уровне кода, зафиксированное в профиле |
| Профили и кеш | Версионированные неизменяемые профили пространств и кеш векторов в SQLite |
| Векторный индекс | Необязательный безопасный `sqlite-vec` `vec0`; при его отсутствии ломаются только семантические команды |
| Identity и приватность | Никакой неявной загрузки корпуса; облако только по явному `--allow-cloud` |
| Инкрементальная индексация | Идемпотентное продолжение с сохранением прогресса и точным учётом стоимости; неопределённый платный POST не повторяется |
| Фильтры и hybrid | Фильтры применяются **до** top-k; гибрид — простое reciprocal-rank объединение |
| Проверки | Офлайн fault-injection плюс отдельная approval-gated реальная приёмка локальной и облачной моделей |
| Gate | Независимый review плана до и существенных срезов после реализации |

### Что не строится 🚫

Не добавляются reranker, cross-encoder, LLM-переранжирование, RAG-чат,
мультивекторные/ColBERT-схемы, гибридный BM25-скоринг вместо rank-объединения,
автоматический выбор между локальным и облачным backend, фоновой автопостинг
индекса, второй ORM или новый конфигурационный язык провайдеров. Не
переписывается FTS5-слой S08 и не меняются роли текста. Количество backend'ов
остаётся ровно **два**, заданных Python-кодом.

## 2. Отправная точка и зависимости 🔍

### Что уже есть на входе 🧱

- Каноническая SQLite-история (`runs`, `parts`, `attempts`, `artifacts`,
  `text_sources`) и производный `search_chunks`/`search_fts` (S08).
- Роли текста и приватность: `tts_script`, `tts_direction`, `asr_transcript`,
  `verification_transcript`, `label`; приватный `asr_context` **не** индексируется.
- Фильтры `--kind/--role/--run/--operation/--provider/--since/--until` до `limit`.
- Чанкинг ~1200 Unicode-символов с перекрытием до 150 и `chunker_version`.
- `SEARCH_MODE_DEFERRED` как текущий честный отказ семантики.

### Необязательные зависимости 🧰

| Слой | Зависимость | Поведение при отсутствии |
|---|---|---|
| Облачный | `sqlite-vec` extra `search` + HTTP-клиент Polza | Локальный FTS и локальная семантика работают; облако недоступно с понятной ошибкой |
| Локальный | extra `search-local`: `sqlite-vec` + `sentence-transformers`/`torch` | Только локальная семантика недоступна; FTS и облако не зависят от Torch |
| Вектор | `sqlite-vec` `vec0` | История и FTS продолжают работать; semantic/hybrid дают понятную ошибку |

Тяжёлые импорты выполняются **только** при выборе соответствующего backend.
`help`, `history`, `search --mode lexical` и офлайн-тесты не импортируют
Torch и не скачивают веса. Команда установки не загружает веса модели
автоматически; подготовка весов — отдельное разрешённое сетевое действие.
`uv sync --all-extras` не является способом проверки продукта: совместимость
проверяется матрицей отдельных extras.

## 3. Архитектура векторного слоя 🏗️

```mermaid
flowchart TB
    Q[search --mode semantic|hybrid]
    Q --> RES[Разрешение профиля]
    RES --> EMB[embed_query]
    RES --> VEC[(vec0 профиля)]
    RES --> FTS[(FTS5 S08)]
    EMB -->|local| LOC[sentence-transformers Qwen 0.6B]
    EMB -->|cloud + allow-cloud| POL[Polza /embeddings 8B]
    VEC --> RANK[Ранжирование]
    FTS --> RRF[RRF объединение]
    RANK --> RRF
    IDX[index build] --> CACHE[(embedding_cache)]
    CACHE --> VEC
    IDX --> EMB2[embed_documents batch]
    EMB2 --> CACHE
```

### Два backend без конструктора провайдеров 🧬

| Backend ID приложения | Реальная модель | Реализация |
|---|---|---|
| `local-qwen3-06b` | `Qwen/Qwen3-Embedding-0.6B` | Необязательная локальная загрузка через `sentence-transformers` |
| `polza-qwen3-8b` | `qwen/qwen3-embedding-8b` | Текстовый HTTP-клиент Polza `/embeddings` |

Интерфейс минимален: `embed_documents(texts)` и `embed_query(query)`, каждый
возвращает векторы и сведения о выполненной операции (backend, model, batch,
usage/cost при наличии). Пользователь не пишет provider bindings YAML.

Официальная карточка Qwen указывает размерность до 1024 для 0.6B и до 4096 для
8B. Локально используется фактическая выдача модели; для облака размерность
берётся из проверенного ответа, а не из предположения. `dimensions` не
передаётся, пока поддержка конкретным маршрутом не подтверждена.

### Явная подготовка query и документов 📝

Qwen различает embedding поискового запроса и документа: официальный шаблон
применяет query-инструкцию к запросам и **не** применяет к документам.
Запрещено усреднять случайный hidden state разговорной модели и называть это
embedding.

- Для `embed_query` используется выбранный официальный query-шаблон
  (например, `Instruct: …\nQuery: …`), для `embed_documents` — чистый текст.
- Pooling, L2-нормализация, точная строка инструкции, model revision и
  размерность фиксируются в профиле индекса.
- Для Polza отдельно проверяется, какой текст уходит upstream и не добавляет ли
  сервис собственную инструкцию. Если это нельзя установить полностью, профиль
  помечается `provider-managed` и **не объявляется** совместимым с прямой
  локальной выдачей.

### Профиль и кеш — версионированные и неизменяемые 🧱

Профиль хранит backend, model ID, revision (или `unknown`/`provider-managed`),
фактическую размерность, query-шаблон, версию preprocessing и chunking, способ
нормализации и fingerprint. Это обычная запись в SQLite, не пользовательский
конфиг конфигов.

- Векторы 0.6B и 8B **никогда** не сравниваются напрямую, даже при совпадающей
  размерности. Смена модели, шаблона или preprocessing создаёт **новый**
  профиль.
- Профиль после первой успешной записи неизменяем; старый индекс остаётся
  доступным, пока новый не проверен. Существующие векторы не обрезаются и не
  дополняются нулями.
- `embedding_cache` хранит float32-представление, привязанное к хешу **точного
  embedding input** и профилю. `vec0` перестраивается из кеша без повторной
  отправки текстов провайдеру.

### sqlite-vec и безопасность загрузки 🗄️

`sqlite-vec` подключается только при обращении к векторному индексу, из
установленного доверенного пакета; после загрузки разрешение динамической
загрузки расширений закрывается. Возможность загрузки проверяется в `doctor`.
Используется `vec0` с cosine distance и отдельной таблицей на immutable
profile/dimension; имя таблицы выводится из внутреннего числового ID, не из
пользовательской строки.

### Фильтры до top-k и гибридное объединение 🧠

- Фильтры (`run`, `operation`, `provider`, даты, роль) применяются **до**
  top-k. Для фильтров, корректно не выразимых в `vec0` выбранной версии,
  используется точное сравнение по заранее отфильтрованному небольшому набору
  кандидатов в SQLite. Нельзя взять глобальные top-k соседей, затем отфильтровать
  и объявить остаток полноценной выдачей.
- Гибрид получает ранжированные результаты FTS и векторного поиска и объединяет
  их reciprocal-rank формулой `1/(60 + rank)`. Сырые BM25 и cosine scores не
  складываются как сопоставимые величины. Начальный размер кандидатов — до 50
  из каждого источника с последующим объединением, дедупликацией и ограничением
  выдачи; ограничивается число фрагментов одного run.
- В JSON сохраняются исходные ранги/тип совпадения и факт неполноты индекса.

### Приватность и identity источника ☁️

- Генерация и ASR **не** запускают embeddings автоматически. После сохранения
  данных приложение показывает, сколько текстов ещё не вошло в выбранный
  профиль; первая индексация — отдельная команда.
- Облачная сборка и облачный query требуют явного `--allow-cloud`. Ключ Polza
  сам по себе **не** разрешает загрузку корпуса.
- `--dry-run` показывает число текстов, суммарный размер и предполагаемые
  запросы, но ничего не загружает и не выдаёт непроверенную точную цену.
- Локальный запрос никогда не использует облачный индекс автоматически и
  наоборот; скрытого переключения при нехватке VRAM нет.
- Связь вектора с источником (run/part/artifact) сохраняется раздельно:
  совпавший текст не означает один аудиофайл. Сумма расходов остаётся у
  первоначального API-вызова и не размножается при переиспользовании кеша.

### Оплачиваемый POST и восстановление 🔐

**Каждый** облачный embedding POST — batch при `index build` **и отдельный
`embed_query` при `search --mode semantic|hybrid`** — подчиняется платным
инвариантам S02/S05. И build, и query требуют `--allow-cloud` **и явно заданный
положительный `--max-rub`** на эту операцию; ключ, профиль или наличие тарифа
не считаются согласием на траты. Для build дополнительно обязателен
`--max-requests`; query ограничен одним POST на вызов поиска. При повторных
вызовах новый cap задаётся явно, а общий cap согласованного набора проверок,
если он установлен, не сбрасывается между вызовами. Если документированной
верхней оценки стоимости POST нет, запрос отклоняется даже при заданном cap.

До каждого POST сохраняется durable attempt/reservation с точной identity
профиля, input-хешами и доказуемым верхним пределом стоимости. Оставшийся cap
проверяется атомарно по оплаченным **и неопределённым** попыткам. Статус после
отправки, но до достоверного ответа остаётся `unknown`: повтор той же
profile/input/operation identity, в том числе новой командой query, не запускает
POST до явного разрешения неопределённой попытки. Полученный bounded private
body/receipt сохраняется
**до** parse и записи векторов, восстанавливается локально из того же attempt
без повторной отправки; usage без проверенной суммы хранится как `NULL`, не как
ноль. Batch cost принадлежит единственной оплаченной попытке и не размножается
по его текстам или cache hits. Dry-run не резервирует и не отправляет POST.

## 4. Этапы реализации 🛠️

Этапы упорядочены так, чтобы сначала зафиксировать пространство векторов и
кеш, затем добавить backend'ы, затем — индекс, поиск и приёмку. Тяжёлый
локальный runtime и облачные вызовы подключаются после офлайн-контрактов.

### S09.0. Зафиксировать базу и контракты 🧭

**Результат:** подтверждённое наличие S08 (FTS5) и `SEARCH_MODE_DEFERRED`,
зафиксированные HEAD/dirty tree и перечень защищаемых контрактов. Офлайн;
код не меняется.

**Проверки:** `search --mode lexical` работает; `--mode semantic|hybrid`
отклоняется; `index status` доступен; FTS не требует optional runtimes.

### S09.1. Схема профилей и кеша (migration) 🧱

**Результат:** аддитивная миграция `embedding_profiles` и `embedding_cache`
поверх S08; профиль immutable; кеш по хешу точного input; FK к создавшей
попытке.

**Проверки:** round-trip профиля; неизменяемость (повтор с другим fingerprint
создаёт новый профиль, не перезаписывает старый); cache hit не создаёт второй
записи; FK/cascade; WAL/migration guard.

### S09.2. Локальный backend 0.6B 🖥️

**Результат:** `local-qwen3-06b` с явным query/document различием, pooling,
нормализацией и ленивым импортом. Веса не скачиваются автоматически.

**Проверки:** размерность и конечность; query-шаблон применён только к запросу;
документ без инструкции; отсутствие `sentence-transformers` даёт понятную
ошибку, не ломая FTS.

### S09.3. Облачный backend 8B через Polza ☁️

**Результат:** `polza-qwen3-8b` через `/embeddings` с проверкой ответа, durable pre-POST attempt/reservation и приватным raw-before-parse replay без второго неопределённого POST.

**Проверки:** количество элементов, `index`, длина каждого вектора, конечность
чисел; переставленные элементы связываются по `index`, а не по позиции массива;
нулевой вектор/NaN/пропуск/неожиданная размерность → ошибка конкретного batch
без повреждения старого индекса; отсутствие разрешения → 0 внешних запросов.

### S09.4. Векторный индекс `vec0` 🗄️

**Результат:** необязательный `vec0` на профиль/размерность; `doctor` сообщает
доступность загрузки расширения; история и FTS не зависят от него.

**Проверки:** profile/dimension изоляция; load failure не ломает FTS; rebuild
из кеша без сети; extension loading закрывается после загрузки.

### S09.5. Инкрементальная индексация и восстановление 🔄

**Результат:** `index build --backend … [--scope …] [--dry-run]
[--allow-cloud --max-rub RUB --max-requests N]`; параметры cap обязательны
для облака, но не для локального backend. Идемпотентное продолжение
недостающих векторов; прогресс `partial`; стоимость batch учитывается один раз.

**Проверки:** повторная индексация неизменённых текстов не вызывает embedding
API; сбой после сохранённого batch не заставляет повторно оплачивать уже
записанные векторы; crash после POST до parse восстанавливает private receipt
локально; неопределённый ответ не повторяет POST; лимит запросов и суммарный
budget сохраняют прогресс; стоимость batch из 16 текстов считается один раз,
unknown cost остаётся `NULL`; cache hit не добавляет списания.

### S09.6. Семантический и гибридный поиск 🔎

**Результат:** `search --mode semantic|hybrid --backend …
[--allow-cloud --max-rub RUB] [--limit …]`; cloud query разрешён только при
обоих флагах и подтверждённой верхней цене единственного POST, backend
разрешается в существующий профиль; отсутствие индекса даёт инструкцию
`index build`, а не скрытый платный вызов.

**Проверки:** filters до top-k; RRF использует ранги; дедупликация; изоляция
профилей (8B-индекс не использует query-вектор 0.6B даже при совпавшем размере);
неполнота индекса видна в JSON; cloud query без cap, после cap exhaustion либо
с unknown POST не выполняет повторный оплачиваемый запрос.

### S09.7. Офлайн fault-injection и оценочный корпус 🔬

**Результат:** версионируемый маленький корпус (русские объяснения, английские
термины, повторённые фразы, одинаковые шаблонные vibe, длинные transcripts,
связанные TTS/ASR-версии) и размеченный набор запросов (≥30). Порог фиксируется
до прогона.

**Проверки:** размерность/NaN/zero norm/дубликат/пропуск `index`; сбой посреди
batch; сбой записи кеша; недоступность `vec0`; откат облака без разрешения;
локальная ошибка не вызывает облачный fallback. Предлагаемый целевой критерий:
хотя бы один размеченный релевантный фрагмент в top-5 минимум для 80%
**ответимых** запросов — это целевой порог проекта, не измеренный результат.

### S09.8. Реальная приёмка и план-гейт 🎧

**Результат:** отдельная **approval-gated** приёмка на реальной локальной
Qwen 0.6B и, с согласия владельца, на реальном Polza 8B; плюс независимый
review существенных срезов.

**Проверки:** реальные веса и runtime на указанной платформе; размерность,
время, результаты корпуса; человеческая оценка релевантности; для облака —
использованная query-инструкция, стоимость и релевантность на согласованном
наборе. В live-отчёт не попадают ключи и приватные исходные данные.

- [ ] Каждый backend имеет отдельные source-only, live и listening статусы.
- [ ] Числового вектора недостаточно: качество подтверждается разметкой.
- [ ] Неподтверждённый upstream-контракт помечается `BLOCKED`, а не «работает
  экспериментально».

## 5. Обязательная матрица проверок ✅

| ID | Сценарий | Что тест реально утверждает | Уровень |
|---|---|---|---|
| N01 | Профиль immutable | Новый fingerprint создаёт новый профиль; старый не перезаписан | SQLite |
| N02 | Cache | Точный input hash + профиль → повтор не вызывает API и не добавляет расходы | Local integration |
| N03 | Размерность/NaN | Неверная размерность, NaN, нулевой norm не попадают в активный индекс | Unit/contract |
| N04 | Index mapping | Дубликат/пропуск `index` в ответе не приводят к смешению векторов | Unit/contract |
| N05 | Query vs document | Query-шаблон применён только к запросу; документ индексируется без инструкции | Unit |
| N06 | Пространства | Поиск в индексе 8B не использует query-вектор 0.6B при совпавшем размере | Unit + sqlite-vec |
| N07 | Приватность | Cloud build/query без `--allow-cloud` **или** `--max-rub` → 0 внешних запросов; локальная ошибка не даёт cloud fallback | Contract |
| N08 | Частичный batch | Durable marker до POST; crash до parse → private raw replay; unknown POST не повторяется; сохранённые векторы не оплачиваются вновь | Contract + SQLite |
| N09 | Инкремент/rebuild | Повторная индексация неизменённых текстов идёт из кеша; rebuild `vec0` без сети | Local integration |
| N10 | Стоимость batch/query | Batch — одна попытка, query — отдельная; unknown = `NULL`, не ноль; explicit RUB cap учитывает оба вида и неопределённые попытки; cache hit бесплатен | SQLite |
| N11 | Фильтры до top-k | Отфильтрованный небольшой набор, а не обрезанный глобальный top-k | Local integration |
| N12 | Hybrid/RRF | Объединение по рангам `1/(60+rank)`, дедупликация, видимые исходные ранги | Local integration |
| N13 | Офлайн fault-injection | Сбои индекса/вектора/расширения не ломают FTS и не создают ложного «полного» индекса | Local integration |
| N14 | Релевантность | Реальные модели проходят заранее размеченный набор по фиксированному порогу | Local model + live |
| N15 | Лёгкий запуск | help/history/FTS не импортируют ML-рантайм и не скачивают веса | Subprocess/network guard |

Проверки должны падать при намеренном возврате дефекта (снятие profile-check,
сравнение 6B/8B, обход `--allow-cloud`, фильтрация после top-k). Процент
покрытия не подменяет эту матрицу.

## 6. Границы доказательств 🔒

- План доказывает **намерение и контракты**, а не работающий поиск. Пока S09.0–S09.8
  не закрыты фактическими прогонами, semantic/hybrid не заявляются доступными.
- Офлайн-тесты используют fixtures, fakes и временные каталоги; они не читают
  `.env`, не ходят в сеть и не загружают модели.
- Реальные локальные веса и облачные вызовы — отдельный approval-gated шаг.
  HTTP 200 не доказывает релевантность; форма вектора не доказывает качество.
- Скрыто обновляемая upstream-модель лишает гарантии абсолютной
  воспроизводимости; в отчёте фиксируются дата и контрольные результаты.

## 7. Риски и решения ⚠️

| Риск | Влияние | Смягчение |
|---|---|---|
| Тяжёлые `torch`/`sentence-transformers` конфликтуют с другими extras | Ломается установка «всё сразу» | Раздельные extras и отдельная проверенная матрица окружений; `search-local` — отдельный venv |
| `sqlite-vec` недоступен в сборке | Нет векторного индекса | Необязательность: FTS и история работают; `doctor` сообщает доступность |
| Скрытая upstream revision/инструкция Polza | Разные пространства при «одной» модели | Профиль `provider-managed`; изоляция; явная приёмка |
| Разные размерности 0.6B/8B | Смешение пространств | Отдельные таблицы и fingerprint; запрет прямого сравнения |
| Неявная утечка приватного корпуса | Приватность | `--allow-cloud` + `--dry-run` + локальный default; никакой автоматизации |
| Повторные списания при rebuild/неопределённом POST | Деньги | Кеш по точному input, durable reservation, raw-before-parse replay, unknown без повтора; batch — одна попытка |
| Фильтр после top-k искажает выдачу | Качество | Фильтры до top-k; явные ранги и неполнота в JSON |
| Локальный GPU/VRAM конфликт с другими движками | Стабильность | Ленивая загрузка, один процесс, отсутствие скрытого cloud fallback |

## 8. Независимый plan-gate 🧷

До начала реализации этот план проходит **независимый review** (не тот же
исполнитель). Гейт закрыт только когда проверено:

- [ ] Scope не расширен в `v0.7.0`: S09 остаётся `DEFERRED`, `SEARCH_MODE_DEFERRED`
      сохраняется до фактической реализации.
- [ ] Два backend'а и их модели названы точно; нет конструктора провайдеров.
- [ ] Профиль/кеш версионированы, неизменяемы и изолированы по пространствам.
- [ ] `sqlite-vec` необязателен и безопасен при загрузке.
- [ ] Приватность: нет неявной загрузки корпуса; облако только по разрешению.
- [ ] Инкрементальная индексация идемпотентна; стоимость не дублируется.
- [ ] Фильтры до top-k; hybrid — rank-based RRF.
- [ ] Офлайн fault-injection и approval-gated реальная приёмка разделены.
- [ ] План не выдаёт себя за разрешение на commit/tag/push/release/model download.

После реализации существенных срезов (S09.1–S09.6) добавляется отдельный
независимый tech-review на фактические байты. Plan-gate и tech-review — разные
события.
